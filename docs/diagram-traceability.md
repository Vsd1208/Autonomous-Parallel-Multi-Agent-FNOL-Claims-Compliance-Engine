# Diagram Traceability

Maps each of the 23 components of the architecture diagram to the code that implements it, the endpoint that exposes it and the tests that cover it. Paths are relative to the repository root; test classes are under each module's `src/test/java/com/guidewire/fnol/...`. Console files are under `frontend/src/`.

Work added after the diagram is listed against the component it belongs to. The few features that go beyond the diagram are listed separately under [Extensions beyond the diagram](#extensions-beyond-the-diagram).

## Scope

The project is an **FNOL** (first notice of loss) engine: it takes in the loss report, runs the agents in two parallel branches, recommends an outcome and a **reserve**, and pre-populates the claim in Guidewire ClaimCenter. It does not pay claims. Payment and the rest of claim handling happen later in ClaimCenter. Every amount the system produces is a reserve recommendation that a human confirms or changes.

| Topic term | Where it is implemented |
|---|---|
| Autonomous | STP path, components 14 and 15: a claim that passes every check is filed without a human (with the advisory-review switch off) |
| Parallel | Async dual-branch engine, component 4 |
| Multi-Agent | Six agents in two branches, components 5–10, joined at the reconciliation gate, component 11 |
| FNOL | Intake, enrichment and duplicate check, components 1–3 and 20 |
| Claims | ClaimCenter pre-population and review sync, components 15 and 17 |
| Compliance | PII redaction, statutory deadlines, governance and the SHA-256 audit trail, components 8, 9, 21–23 |

## Extensions beyond the diagram

These features are not drawn in the diagram. They extend Human Review Point 3 and the hand-off to ClaimCenter. None of them changes the autonomous, parallel, multi-agent core (components 4–11, 14 and 15).

| Extension | Why it was added | Where it attaches | Implementation | Tests |
|---|---|---|---|---|
| Damage inspection (assign an inspector, inspector's report, decide with the inspected figure) | Photos cannot always show whether damage is from this accident or what the repair costs, especially when the amount claimed is above the AI estimate or there may be earlier damage | After Human Review Point 3 (16), next to "investigation": the claim waits in `INSPECTION_ASSIGNED` and returns to `HUMAN_REVIEW` with the report. In production this step would usually run in ClaimCenter | `InspectionController`, `InspectionEntity` (V10), console `components/Inspection.tsx`, Inspection section and Desktop "Awaiting Inspection" queue | `InspectionWorkflowTest` |
| Supplementary photo upload link | "Request more photos" had no way for the claimant to send them | Human Review Point 3 (16), "request information" | `UploadRequestController`, `UploadRequestEntity` (V13), console `pages/UploadPage.tsx` (claimant), `components/PhotoRequests.tsx` (adjuster) | `UploadRequestWorkflowTest` |
| Retry of a failed ClaimCenter decision sync | A ClaimCenter outage must not lose the adjuster's decision | Component 17 | `POST /api/v1/fnol/{id}/claimcenter-sync`, Summary "Retry sync" | `ClaimCenterSyncAndQueueTest.failedSyncCanBeRetried` |
| Persistent mock ClaimCenter and Postgres volume | Restarts lost the mock's claims, so decision syncs failed with 404 | Test infrastructure for component 17 | `ClaimCenterStore`, `claimcenter-schema.sql`, `postgres_data` volume in `docker-compose.yml` | `ClaimCenterPersistenceTest` |
| Vision evaluation and calibration tooling | Measures how far Gemini's confidence can be trusted on labelled real photos | Offline support for component 5 | `tools/vision-eval`, `VisionConfidenceCalibrator` (inactive until a calibration file is shipped) | `VisionConfidenceCalibratorTest` |

**Limits that come with the extensions:** in this prototype the inspector reports with the adjuster's token (production needs a separate inspector role), and the inspector roster is synthetic.
